# ✅ Local Agent Chat v1 — документация проекта

## 1. Назначение проекта

**Local Agent Chat** — локальный пользовательский интерфейс для работы с несколькими LLM-агентами через один чат. Проект задуман как базовый шаблон: интерфейс, хранение истории, память, работа с файлами и общий механизм запуска агентов реализованы один раз, а прикладные агенты подключаются поверх этой основы.

На текущем этапе проект ориентирован на локальную разработку. Интерфейс построен на Chainlit, агентный слой — на LangChain/LangGraph, а модель по умолчанию запускается через Ollama. Код агентов зависит от общего интерфейса `BaseChatModel`, поэтому локальную модель можно позже заменить на внешний API без переработки основной архитектуры.

Версия v1 включает два агента. **General** — универсальный помощник для обычных задач. **Analyst** — пример специализированного агента: он умеет работать со структурированными данными, использовать загруженную документацию как базу знаний и формировать HTML-отчёт с EDA.

## 2. Возможности v1

В текущей версии реализованы:

- постоянная история диалогов в Chainlit и восстановление чата после перезапуска;
- выбор агента при создании нового диалога;
- память текущего диалога через LangGraph checkpoints;
- поиск по предыдущим диалогам пользователя;
- загрузка файлов в отдельную область каждого чата;
- чтение текстовых файлов и PDF с текстовым слоем;
- работа Analyst с CSV, TSV и XLSX через pandas;
- локальный поиск по загруженным PDF/TXT/MD и другим текстовым документам;
- формирование HTML-отчёта с EDA и выдача его пользователю как файла;
- раздельное хранение истории интерфейса, памяти агента, файлов, базы знаний и созданных артефактов;
- очистка связанных данных при удалении чата.

OCR и работа с изображениями в v1 сознательно не входят.

## 3. Общая схема

```text
                           Chainlit UI
                               │
                               ▼
                            app.py
                               │
                               ▼
                         AgentRuntime
                               │
                               ▼
                         AgentRegistry
                       ┌───────┴────────┐
                       │                │
                    General          Analyst
                       │                │
                       └───────┬────────┘
                               ▼
                      LangChain agent
                               │
                  ┌────────────┼─────────────┐
                  │            │             │
                Model        Tools       LangGraph
                  │            │             │
                Ollama       Files        Checkpoints
                              Memory
                              RAG
                              Analytics
```

`app.py` отвечает в основном за связь Chainlit с приложением. Основная логика находится в пакете `local_agent_chat`.

Пакет `local_agent_chat` является ядром проекта. В нём находятся запуск агентов, память, файловая система чатов, поиск по истории, база знаний, аналитика и работа с результатами.

## 4. Жизненный цикл диалога

При создании нового чата пользователь выбирает профиль агента. Chainlit создаёт идентификатор диалога, после чего приложение связывает его с выбранным агентом и с отдельной веткой памяти LangGraph.

Связь описывается объектом `ChatBinding`:

```text
user_id
chat_id
agent_id
memory_thread_id
```

`chat_id` относится к диалогу в интерфейсе, `agent_id` определяет используемого агента, а `memory_thread_id` связывает диалог с состоянием LangGraph. Сейчас для обычного чата `chat_id` и `memory_thread_id` совпадают, но они специально разделены на уровне архитектуры.

Когда пользователь отправляет сообщение, происходит следующий путь:

```text
Сообщение пользователя
        │
        ├── сохранение прикреплённых файлов
        │
        ▼
   AgentRuntime
        │
        ├── получение нужного агента из AgentRegistry
        ├── загрузка состояния текущего диалога
        └── передача сообщения агенту
                │
                ▼
          model / tools
                │
                ▼
          итоговый ответ
                │
        ┌───────┴────────┐
        ▼                ▼
 Chainlit UI      runtime-history
```

Для одного `memory_thread_id` одновременно разрешён только один выполняющийся запрос. Это защищает состояние диалога от параллельной записи двух turn'ов.

## 5. Агенты

Агенты регистрируются в `AgentRegistry`. Описание агента хранится в `AgentDefinition`: там находятся его имя для интерфейса, системный промпт, фабрика модели, набор инструментов и функция сборки.

Граф агента создаётся не на каждое сообщение и не на каждый чат. Для каждого `agent_id` он собирается один раз и затем переиспользуется. Состояние разных диалогов при этом остаётся раздельным за счёт `memory_thread_id`.

В v1 зарегистрированы два агента.

| Агент | Назначение | Дополнительные возможности |
|---|---|---|
| General | Универсальный помощник | файлы текущего чата, поиск по прошлым диалогам |
| Analyst | Анализ данных и документации | всё из General + RAG по документам + CSV/TSV/XLSX + HTML EDA |

Выбор агента фиксируется за конкретным чатом. После перезапуска приложения старый диалог восстанавливается с тем же агентом, а не с текущим выбором пользователя в интерфейсе.

## 6. Память

В проекте используются два разных механизма памяти.

### ⭐ Память текущего чата

LangGraph сохраняет состояние агента в `checkpoints.sqlite3`. Основная часть текущего состояния — история сообщений, но механизм checkpoints рассчитан на состояние графа в целом.

Ключом служит `memory_thread_id`. Благодаря этому агент продолжает тот же разговор после перезапуска приложения.

```text
Chat A → thread A → свои checkpoints
Chat B → thread B → свои checkpoints
```

### ⭐ Память между чатами

Завершённые turn'ы дополнительно записываются в `runtime-history.sqlite3`. По ним строится полнотекстовый индекс SQLite FTS5.

Агент не получает все старые диалоги автоматически. При необходимости он вызывает два инструмента: сначала ищет подходящие прошлые turn'ы, затем читает найденный фрагмент подробнее.

Поиск ограничен текущим пользователем и исключает текущий чат. Такой подход не раздувает контекст каждого запроса и отделяет текущую память диалога от истории предыдущей работы.

## 7. Работа с файлами

Загруженные пользователем файлы копируются из временного хранилища Chainlit в постоянную область конкретного чата:

```text
.local-agent-chat/
└── sandboxes/
    └── <chat_id>/
        ├── files/
        └── artifacts/
```

`files/` содержит входные файлы пользователя. Агент получает только чтение этой области. Доступ к произвольным файлам компьютера не предоставляется.

`artifacts/` предназначен для файлов, которые создаёт приложение от имени агента. В v1 туда записываются HTML-отчёты Analyst. Агент не имеет общего инструмента `write_file`; запись выполняется только через разрешённые прикладные функции.

Для имён файлов и путей используются проверки, которые не позволяют выйти за пределы текущего чата через конструкции вроде `../` или символические ссылки.

По умолчанию размер одного загружаемого файла ограничен 20 МБ, а общий объём файлов одного чата — 200 МБ.

## 8. Чтение TXT и PDF

Текстовые файлы читаются как обычный текст. Поддерживаются UTF-8, UTF-8 с BOM и CP1251.

PDF обрабатывается в два этапа. Основной способ — PyMuPDF. Если он не справляется с конкретным документом, используется `pypdf` как запасной вариант.

Файл возвращается агенту не обязательно целиком: `read_chat_file` умеет читать ограниченное число строк с указанного смещения. Это позволяет работать с крупными документами без загрузки всего текста в контекст модели.

Сканированные PDF без текстового слоя не распознаются. В таком случае система явно сообщает, что OCR в v1 не настроен.

## 9. База знаний и RAG

RAG в v1 реализован локально и не использует отдельную embedding-модель или векторную базу. Это сделано специально, чтобы базовый шаблон не требовал второй модели и дополнительного тяжёлого окружения.

Документы текущего чата индексируются в `knowledge.sqlite3`. Поддерживаются PDF с текстовым слоем и различные текстовые форматы: TXT, MD, JSON, YAML, XML, SQL, Python и некоторые другие.

При первом обращении к базе знаний система просматривает подходящие файлы текущего чата, извлекает текст, разбивает его на фрагменты и создаёт полнотекстовый индекс SQLite FTS5. Для уже проиндексированного неизменившегося файла повторная индексация не нужна: состояние определяется в том числе по SHA-256 файла.

Поиск выполняется только внутри текущего пользователя и текущего чата. Для модели доступен простой интерфейс `search_knowledge`, поэтому в будущем внутренний механизм можно заменить на embeddings или гибридный поиск без изменения интерфейса Analyst.

Важно различать RAG и память между чатами. RAG ищет информацию в загруженных документах текущего чата. Cross-chat memory ищет сведения в предыдущих разговорах пользователя.

## 10. Агент Analyst

Analyst служит одновременно полезным примером и проверкой того, что базовая архитектура действительно позволяет подключать специализированных агентов.

Основной сценарий — пользователь загружает набор данных CSV/XLSX и при необходимости PDF или текстовый документ с методологией, описанием полей или бизнес-правилами. Агент сначала изучает данные, затем при необходимости обращается к документации и после этого строит EDA-отчёт.

Работа со структурированными данными выполняется через `DataAnalysisService`. Произвольный Python или shell модели не доступны. Такой подход ограничивает возможные действия агента и делает поведение более предсказуемым.

### ⭐ `inspect_dataset`

Инструмент предназначен для первичного просмотра выборки. Он показывает размер данных, типы столбцов, число дублей, пропуски и небольшой пример строк. Для Excel можно указать конкретный лист; без указания используется первый лист.

### ⭐ `build_eda_report`

Инструмент строит self-contained HTML-отчёт. В него входят общий обзор выборки, качество столбцов, пропуски, числовые статистики, распределения числовых признаков, популярные значения категориальных признаков, сильные корреляции, матрица корреляций, примеры строк и при необходимости отдельный раздел по target.

Графики сохраняются непосредственно внутри HTML в виде встроенных изображений. Дополнительные PNG рядом с отчётом не требуются.

После создания файла `app.py` обнаруживает новый артефакт и прикрепляет его к сообщению Chainlit, поэтому пользователь получает HTML непосредственно в интерфейсе.

По умолчанию Analyst ограничивает набор данных 200 000 строками и 200 столбцами. Ограничения можно менять через переменные окружения.

## 11. Хранение данных

Всё локальное состояние по умолчанию находится в `.local-agent-chat/`.

| Путь | Что хранится |
|---|---|
| `checkpoints.sqlite3` | состояние LangGraph и память текущих чатов |
| `chainlit.sqlite3` | пользователи, диалоги, сообщения и другая история интерфейса |
| `runtime-history.sqlite3` | завершённые turn'ы для поиска по прошлым чатам |
| `knowledge.sqlite3` | индекс документов для RAG Analyst |
| `sandboxes/<chat_id>/files/` | загруженные пользователем файлы |
| `sandboxes/<chat_id>/artifacts/` | созданные агентом результаты, например HTML EDA |
| `blobs/` | файлы, которые нужны Chainlit для отображения вложений в истории |

Хранилище интерфейса и рабочие файлы агента намеренно разделены. Chainlit может менять способ хранения UI-элементов, не затрагивая sandbox агента.

При удалении чата приложение очищает связанную с ним память LangGraph, историю для cross-chat retrieval, файлы sandbox и индекс базы знаний. Удаление проходит через application-level cleanup, а не ограничивается только удалением записи из интерфейса.

## 12. Основные части проекта

```text
app.py
│
├── Chainlit hooks
├── выбор агента
├── загрузка файлов
├── resume/history
└── выдача артефактов

local_agent_chat/
├── bootstrap.py          сборка приложения и регистрация агентов
├── agent_registry.py     описания агентов и кэш готовых графов
├── runtime.py            выполнение одного запроса
├── models.py             создание LLM
├── memory.py             память текущего чата
├── runtime_history.py    поиск по прошлым чатам
├── sandbox_files.py      файлы текущего чата
├── file_readers.py       чтение текста и PDF
├── knowledge.py          база знаний Analyst
├── analytics.py          pandas-анализ и EDA
├── artifacts.py          контролируемая запись результатов
├── agents/               описания General и Analyst
├── prompts/              системные промпты
└── tools/                инструменты, доступные моделям
```

Это обзор структуры, а не подробное описание каждого модуля. Отдельная методичка по созданию нового агента и взаимодействию модулей может быть построена поверх этой схемы.

## 13. Chainlit и интерфейс

Chainlit используется как готовый веб-интерфейс. Он отвечает за отображение сообщений, список диалогов, выбор профиля агента, вложения и восстановление истории.

Собственный SQLite data layer используется потому, что история интерфейса должна переживать перезапуск процесса. В проекте также есть локальное blob-хранилище для прикреплённых к сообщениям файлов.

Для локальной разработки включена простая авторизация `local-user`. Она доверяет любому запросу, который дошёл до процесса Chainlit. Поэтому текущую конфигурацию следует использовать только локально или за внешней защищённой точкой входа. Перед публикацией приложения требуется заменить её на нормальную авторизацию.

## 14. Конфигурация

Основные настройки задаются через `.env`.

```env
OLLAMA_MODEL=qwen3-coder:30b
OLLAMA_BASE_URL=http://localhost:11434

APP_DATA_DIR=.local-agent-chat
CHAINLIT_AUTH_SECRET="<generated-secret>"
LANGGRAPH_STRICT_MSGPACK=true

MAX_UPLOAD_FILE_MB=20
MAX_CHAT_FILES_MB=200

ANALYST_MAX_DATASET_ROWS=200000
ANALYST_MAX_COLUMNS=200
```

`CHAINLIT_AUTH_SECRET` создаётся один раз командой:

```bash
chainlit create-secret
```

После генерации значение нужно вручную добавить в `.env`.

## 15. Установка и запуск

Требуется Python 3.12/3.13-совместимое окружение с зависимостями из `requirements.txt` и работающий Ollama.

```bash
python -m venv .local-chat-env
source .local-chat-env/bin/activate
pip install -r requirements.txt
```

После настройки `.env` приложение запускается командой:

```bash
chainlit run app.py
```

Для разработки можно использовать режим автоматической перезагрузки:

```bash
chainlit run app.py -w
```

## 16. Пример работы Analyst

Пользователь создаёт чат с профилем `Analyst`, загружает `sample.xlsx` и `methodology.pdf`, после чего пишет:

> Проведи EDA выборки. Target — `target`. Используй методологию при интерпретации качества данных и сформируй HTML-отчёт.

Ожидаемый сценарий работы:

```text
sample.xlsx
    ↓
inspect_dataset
    ↓
methodology.pdf
    ↓
search_knowledge
    ↓
build_eda_report
    ↓
краткие выводы в чате
+
eda_sample.html
```

Если документация не нужна для ответа, агент может выполнить анализ без RAG. Если в запросе есть бизнес-определения или правила качества данных, Analyst должен использовать загруженную методологию до интерпретации результата.

## 17. Безопасные границы v1

Проект намеренно ограничивает возможности модели. Агент не получает произвольный shell, выполнение Python-кода, доступ ко всей файловой системе компьютера или общий инструмент записи файлов.

Файлы доступны только внутри конкретного чата. Создание выходных файлов выполняется через отдельные сервисы с заранее определённой областью записи.

Текст из файлов и найденных документов считается данными, а не инструкциями. Системные промпты прямо запрещают воспринимать команды внутри PDF/TXT или старых диалогов как инструкции более высокого приоритета.

Текущая локальная авторизация не предназначена для открытого сетевого доступа. Это одна из границ между локальной v1 и будущим production-развёртыванием.

## 18. Ограничения текущей версии

OCR и анализ изображений отсутствуют. Сканированный PDF без текстового слоя прочитать нельзя.

PDF рассматривается как текстовый документ и источник знаний. Таблицы из PDF автоматически не переводятся в pandas.

Для анализа данных поддерживаются CSV, TSV и XLSX; старый формат `.xls`, Parquet и другие форматы пока не входят в базовую реализацию.

RAG основан на обычном полнотекстовом поиске SQLite FTS5. Семантический поиск по embeddings в v1 не используется.

В Analyst нет произвольного выполнения кода. EDA ограничен тем набором расчётов, который реализован в `DataAnalysisService`.

В проекте пока нет полноценной визуализации tool calls/streaming, revision/rollback состояния, автоматического summarization длинных диалогов, отдельной curated long-term memory, production-аутентификации и серверного хранилища уровня Postgres.

## 19. Статус v1

Текущую версию можно считать завершённой базой для локального UI-приложения с подключаемыми агентами. Платформенная часть уже отделена от прикладных возможностей: интерфейс, хранение, память, файлы и запуск агента являются общими, а `General` и `Analyst` отличаются в основном системным промптом и доступным набором инструментов.

`Analyst` выступает проверочным примером этой архитектуры: он использует те же общие механизмы, но добавляет собственную работу с данными, базой знаний и выходными артефактами без изменений основного runtime.

Следующий уровень развития проекта логично рассматривать уже как v2, а не как обязательное завершение основы.
